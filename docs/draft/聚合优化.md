目前的需求是，排行榜数据不用频繁刷新，可以几个小时刷新一次，甚至可以每天刷新一次。具体取决于crawler的运行频率。crawler会不断写入数据库，可能会影响api的响应时间。

目前crawler必须至少运行完一个tier的所有phase，才能有有效可聚合的数据。这在api限速的情况下（同时也取决于crawler运行的频率，当前为抓取的比赛书），这可能需要几个小时甚至更久。导致排行榜的数据必须很久才能刷新一次。后期可能会改成一个match抓完所有数据再下一个match，这样隔几个小时就可以收集到一定数量的数据，可以以较快的频率刷新排行榜数据。但由于api限速，注定了排行榜数据不会频繁刷新。

下面有几个方案：
1. rankings page 在redis内常驻，不设置过期时间，为所有的rankings页面（2 versions × 2 regions × 5 tiers × 6 position modes（overall + 5 positions = 120 个页面）。当需要更新数据时，直接用现在10s左右的聚合聚合一次，然后更新redis内的排行榜数据。

2. rankings page 在redis内常驻 （120个页面），不设置过期时间。单独建一个聚合小表，每次新的比赛数据入库时，聚合小表会更新对应的英雄数据，然后在rankings page需要更新时，直接用聚合小表的数据聚合一次，然后更新redis内的排行榜数据。关于小表聚合也可以有很多方式。

3. rankings 所有page在redis内常驻如果空间不够只能部分页面。这就需要cold有较快的聚合速度。必须使用聚合小表的方式。

主要有两个考量：
1. 用户获取api的数据越快越好
2. 由于后台的crawler可能会不断写入数据库，要保证在crawler运行的时候api的响应时间不会受到影响。

可能的风险：120个页面的内存占用

目前为了解决rankings页面cold start的请求时间过长的问题数据，提出了以下几点改进措施：
1.  redis内常驻所有的rankings页面数据（2 versions (数据库里面最新的两个版本) × 2 regions （KR, NA） × 5 tiers × 6 position, (overall + 5 positions) × 1 modes = 120 个页面），不设置过期时间。当需要更新数据时，直接用现在10s左右的聚合聚合一次，然后更新redis内的排行榜数据。
2. 建立一些聚合小表。按一定方式维护更新，对于api 请求如果redis重启或者关闭，通过小表聚合数据，减少cold start的请求时间。小表的聚合方式有很多种，具体的聚合方式需要根据实际情况来定。


### 排行榜汇总表 （Rankings Rollup Tables）


#### 1. 设计目标
预聚合表只保存可累加的原子统计：

- 不保存最终 120 页。
- 不保存 winRate、pickRate、banRate、losses 等派生结果。
- 不按 master_plus 等重叠 tier group 存储。
- API 不再扫描宽大的 match_participants 和 match_bans。
- minGames 和 positionThreshold 可以在查询时调整，不需要重建预聚合表。

#### 2. 原子维度
所有表都基于以下原子 scope：

queue_id
version
region
tier_bucket

例如：

420 / 16.13 / KR / MASTER
420 / 16.13 / KR / GRANDMASTER
420 / 16.13 / KR / CHALLENGER

这里存的是原始 avg_tier，不直接存：

master_plus
grandmaster_plus

因为：

master_plus = MASTER + GRANDMASTER + CHALLENGER
grandmaster_plus = GRANDMASTER + CHALLENGER

建议不仅保存最高三个 tier，而是保存数据库里出现的全部 avg_tier。avg_tier IS NULL 可以归入一个明确的：

UNCLASSIFIED

这样将来支持其他 tier 或 ALL 时不需要改表结构。

目前的组合数 （1 queue × 2 version × 2 regions × （10 avg_tier + 1 unclassified））= 44 个 scope。

#### 为什么保存 kda_contribution_sum

当前 SQL 的 KDA 是：

AVG((kills + assists) / max(deaths, 1))

因此正确的预聚合方式是：

KDA = SUM(每个 participant 的 KDA contribution) / SUM(games)

不能改成：

(SUM(kills) + SUM(assists)) / SUM(deaths)

两者语义不同。

kills_sum/deaths_sum/assists_sum 虽然当前排行榜不直接使用，但成本很低，并能支持未来切换 KDA 公式及数据校验。

#### 4. 表二： 英雄禁用统计

```sql
CREATE TABLE rankings_champion_ban_rollup (
    queue_id        integer NOT NULL,
    version         text    NOT NULL,
    region          text    NOT NULL,
    tier_bucket     text    NOT NULL,

    champion_id     integer NOT NULL,
    ban_matches     bigint  NOT NULL,

    PRIMARY KEY (
        queue_id,
        version,
        region,
        tier_bucket,
        champion_id
    )

```

这里保存的是：

COUNT(DISTINCT match_id)

而不是 ban 事件数量。

必须单独建表，不能只把 ban 数放进英雄位置表。原因是：

- ban 本身没有 position；
- 一个英雄可能在某个 tier 中只被 ban、没有被选；
- 查询 master_plus 时，这部分 ban 仍然必须计入 banRate。

- 非标准比赛数据混入。

## 对 pickRate 的影响

假设三场比赛中，Ahri 有一场走 MIDDLE：

当前 position 统计：

MIDDLE totalMatches = 2
Ahri MIDDLE games = 1
pickRate = 1 / 2 = 50%

如果所有 position 统一使用 overall：

overall totalMatches = 3
Ahri MIDDLE games = 1
pickRate = 1 / 3 = 33.33%

所以这不仅是存储方式不同，还会影响 position 页的 pickRate。

#### 6. API 如何组合页面

以：
```
queue=420
version=16.13
region=KR
tier=master_plus
position=overall
minGames=20
positionThreshold=5
```
为例。

1. 确定原子tiers

```
MASTER
GRANDMASTER
CHALLENGER
```

2. 计算英雄总体数据

从 rankings_champion_position_rollup 按英雄汇总所有位置和三个 tier：

```
games = SUM(games)
wins = SUM(wins)
losses = games - wins

winRate = wins / games
kda = SUM(kda_contribution_sum) / games
```

3. 计算英雄有效位置

先按英雄和位置汇总：

```
position percentage =
    champion position games / champion total games × 100
```

然后应用请求中的：

positionThreshold = 5

因此 threshold 可以在运行时改变，不需要重建 rollup。

4. 计算比赛总数

  从 rankings_match_count_rollup 中取三个 tier 的 OVERALL：

```
  totalMatches =
      MASTER total
    + GRANDMASTER total
    + CHALLENGER total
```

  因为一场比赛只有一个原子 avg_tier，所以不同 tier bucket 之间可以安全相加。

5. 计算ban

  从 rankings_champion_ban_rollup 汇总三个 tier：

```
  banMatches = SUM(ban_matches)
  banRate = banMatches / totalMatches
```

6. 应用 minGames

```
  WHERE games >= 20
```
  所以 minGames 同样可以动态调整。

### 6. 英雄名字不放在 rollup 表中

  预聚合表建议只保存：

  champion_id

  英雄名称属于维度数据，不是统计数据。尤其有多语言需求时，应该由独立的英雄目录提供：

  champion_catalog
  - champion_id
  - locale
  - champion_name
  - data_version

  否则将来增加中文、英文、韩文时，会导致整套排行榜统计按语言重复存储。

### 九、第一版暂定的边界

  这版设计暂时不确定：

  - Redis 如何生成页面；
  - rollup 表是增量更新还是批量重建；
  - 是否加入 snapshot/generation；
  - 最新两个版本如何淘汰；
  - 刷新任务由 crawler、独立 worker 还是定时任务触发。

  先把表的统计语义和原始 SQL 对齐。下一步应该针对这三张表写出“从现有大表生成 rollup 的 SQL”，然后在固定数据集上验证：

  1. 预聚合结果与当前 rankings API 全字段一致；
  2. overall 和五个 position 全部一致；
  3. 五种 tier group 全部一致；
  4. cold 查询从当前约 8 秒下降到什么水平。

  ## Summary

  将 rankings rollup 改为只统计严格合格的 queue 420 对局，并让 champion、ban、match count 三类聚
  合共享同一份 eligible match 集合。重写尚未提交的 migration 019，删除冗余字段和按位置重复计数，
  增加可审计的排除原因，并通过真实 PostgreSQL 集成测试验证 schema、过滤规则、聚合结果和幂等性。

  ## Schema 与查询调整

  - rankings_champion_position_rollup
      - 保留维度：queue_id, version, region, tier_bucket, champion_id, champion_name,
        team_position。

      - 保留指标：games, wins, kda_contribution_sum。
      - 删除未使用的 kills_sum/deaths_sum/assists_sum 和冗余的 kda_contribution_count；严格事实校

        SUM(games)。

      - CHECK：queue 必须为 420，tier/position 必须在固定枚举内，文本非空，champion ID 为正，
        games > 0，0 <= wins <= games，KDA sum 非负。

  - rankings_champion_ban_rollup
      - 保留当前原子维度及 ban_matches。
      - CHECK 固定 queue、合法 tier、正 champion ID、ban_matches > 0。
