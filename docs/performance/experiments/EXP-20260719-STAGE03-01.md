## 初始执行计划结果

| 指标 | overall | MIDDLE position |
|---|---:|---:|
| Execution Time | 10,243.550 ms | 4,705.646 ms |
| filtered matches | 140,952 | 140,952 |

按 PostgreSQL 默认 8 KiB block 折算，overall 约读取 628 MiB、写入 550 MiB 临时数据；
position 约读取 278 MiB、写入 288 MiB。该数值是节点累计 buffer 计数，用于比较，
不能当作唯一临时文件的精确尺寸。

### 主要节点

1. `matches` 使用 `idx_matches_region_status` 后再过滤 queue/version/tier：overall 约
   185 ms，position 约 30 ms，不是主导成本。
2. `match_participants` 顺序扫描 2,863,320 行并读取约 238,000 blocks。overall 的
   hash join 分成 32 batches；position 需要外部排序后 merge join。
3. `match_bans` 顺序扫描全表，hash join 同样分成 32 batches；按
   `(champion_id, match_id)` 去重前的外部排序落盘约 44 MiB。
4. overall 的 `COUNT(DISTINCT base.match_id)` 额外执行约 24 MiB external merge，且
   materialized `base` 被 totals、champion 和 position 聚合重复读取。
5. 估算偏差明显：overall base 估算 5,412,628 行，实际 1,409,520 行；position
   base 估算 1,078,916 行，实际 281,887 行，均约高估 3.8 倍。

## 判定

初始假设成立。首个候选采用会话级 `work_mem` 单变量实验，先验证消除 32-batch hash
和外部排序能带来多少收益；它不会改变查询语义或索引。若收益不足，再独立验证 SQL
重写（优先消除 `COUNT(DISTINCT base.match_id)` 和不必要的重复扫描），之后才评估覆盖
索引及其 Worker 写入/空间代价。

## 下一步

## 候选 1：会话级 `work_mem = 128MB`

在显式事务中设置 `SET LOCAL work_mem = '128MB'`，以完全相同的查询和参数执行一次
诊断计划，随后 `ROLLBACK`。

| 指标 | 默认 overall | 128MB overall | 默认 position | 128MB position |
|---|---:|---:|---:|---:|
| Execution Time | 10,243.550 ms | 9,954.152 ms | 4,705.646 ms | 10,890.464 ms |
| temp read/write | 80,348 / 70,424 | 0 / 0 | 35,525 / 36,917 | 0 / 0 |
| 最大 hash memory | 约 8 MB，32 batches | 256,265 kB，1 batch | 约 8 MB，32 batches | 173,816 kB，1 batch |

判定：**拒绝**。消除临时 I/O 后，overall 单次仅改善约 2.8%；position 单次结果受磁盘
冷读和执行顺序影响而明显变差，不能证明收益。更重要的是，一个查询内的 hash 节点可
占用约 256 MB 和 174 MB，`work_mem` 又按执行节点和并发连接计算，直接作为 API
配置存在不可接受的并发内存风险。该设置没有写入数据库或应用配置。

## 候选 2：从 `filtered_matches` 计算 total matches

单独将两个查询的 `totals` CTE 从：

```sql
SELECT COUNT(DISTINCT match_id) FROM base
```

改为：

```sql
SELECT COUNT(*) FROM filtered_matches
```

数据前提检查显示 140,952 个 filtered match 中，没有缺少有效 participant 的 match，
且每个 match 恰好有 10 个 `champion_id > 0` participant。原始 SQL 与候选 SQL 的两个
完整结果流 SHA-256 均为
`dc314bb525a805e09a68fc7e57eab7fd82e7f48062c4159ea18f3c30af1eb92f`。

| 指标 | baseline | candidate | 变化 |
|---|---:|---:|---:|
| overall execution | 10,243.550 ms | 6,005.971 ms | -41.4% |
| overall temp read | 80,348 blocks | 64,575 blocks | -19.6% |
| overall temp written | 70,424 blocks | 64,187 blocks | -8.9% |
| position execution | 4,705.646 ms | 4,501.783 ms | -4.3% |
| position temp read | 35,525 blocks | 33,438 blocks | -5.9% |
| position temp written | 36,917 blocks | 34,415 blocks | -6.8% |

候选消除了 totals 对 materialized `base` 的一次读取以及
`COUNT(DISTINCT base.match_id)` 的 external merge。单次诊断达到预期且结果逐字段等价，
因此使用 sqlc 1.27.0 生成 candidate API image，并完成正式重复测试。
