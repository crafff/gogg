# 阶段 8：CI、发布和持续维护

## 目标

把低成本正确性检查放入每次提交，把稳定的性能回归放入定时或发布流程，并定义
灰度和回滚条件。

## 分层计划

- 每次提交：单元、race、lint、契约测试和微基准。
- 每日或手动：固定数据集的小规模 k6 回归。
- 发布前：独立性能环境的完整负载与故障测试。
- 上线后：canary 与旧版本在相同流量窗口对比。

## 门禁指标

同时约束正确率、错误率、p95/p99、吞吐量、CPU、内存、PostgreSQL 查询量/时间
和 Redis 命中率。不能通过增加大量资源消耗换取延迟数字改善。

## 回滚条件

- 5xx 或 GraphQL error rate 超阈值。
- p95 相对基线显著退化并持续多个窗口。
- 数据库负载、连接池等待或缓存错误异常上升。
- 数据正确性或 API 契约回归。

## 验收标准

- 门禁使用固定数据、明确统计窗口和可解释阈值。
- 失败结果可以定位到原始 artifact 和 commit。
- canary 和回滚步骤经过演练。
