# EXP-20260719-ROLLUP-01：rankings rollup 初版

- 日期：2026-07-19
- 状态：初版通过；pickRate 分母为有意的契约变更
- 目标：用窄的原子 rollup 替代在线 API 对 `match_participants` 和
  `match_bans` 的大表扫描，并保留按 position 独立统计的 `totalMatches`。

## 实现

新增三个数据粒度：

- `rankings_champion_position_rollup`：原子 tier × champion × position 的
  games、wins、kills/deaths/assists 和 KDA contribution。
- `rankings_champion_ban_rollup`：原子 tier × champion 的 distinct ban matches。
- `rankings_match_count_rollup`：原子 tier × position mode 的 distinct matches
  和 participant slots。

`rankings-rollup` 命令在一个 PostgreSQL 事务中删除旧派生行并重建三张表；
API 查询只组合 rollup。`totalMatches` 使用 position-specific distinct matches，
`pickRate` 使用同一 position 的 participant slots，`banRate` 继续使用 distinct
matches。

## 分母验证

KR / 16.13 / master_plus 中，每个正常 position match 约有两个 participant，
overall 约有十个：

| mode | matches | participants | participants/match |
|---|---:|---:|---:|
| OVERALL | 140,952 | 1,409,520 | 10.0000 |
| TOP | 140,951 | 281,861 | 1.9997 |
| JUNGLE | 140,952 | 281,893 | 1.9999 |
| MIDDLE | 140,952 | 281,887 | 1.9999 |
| BOTTOM | 140,952 | 281,886 | 1.9999 |
| UTILITY | 140,952 | 281,872 | 1.9998 |

因此使用 distinct matches 作为 pickRate 分母时，各单位置页面合计约 200%，
overall 合计 1000%；使用 participant slots 后，未逐行舍入的合计均为 100%。API
逐英雄保留两位小数后，实测合计为 99.90%～100.03%。

## 正确性

- 切换 pickRate 分母前，旧 API 与 rollup 的 60 组合对比中 58 个逐字段相等。
- 两个 TOP 组合的运行中旧镜像返回 overall total 140,952；直接从原始表执行
  position-specific distinct 查询得到 140,951，与 rollup 一致。
- 切换 participant-slot pickRate 后，pickRate 与旧 API 是有意差异；games、wins、
  losses、KDA、ban 聚合和 position-specific totalMatches 的原始统计语义不变。
- 最终 REST/GraphQL 契约矩阵：60/60 checks，120 HTTP 请求，0 mismatch，0 failure。

## Redis-cold GraphQL 性能

每次运行前清空 Redis，执行 KR / 16.13 / master_plus / overall 单请求：

| run | duration |
|---|---:|
| 01 | 27.851 ms |
| 02 | 13.218 ms |
| 03 | 16.325 ms |
| **中位数** | **16.325 ms** |

原始 SQL baseline cold 中位数为 8.158 秒。rollup 中位数约快 500 倍，延迟降低
约 99.8%。三次 checks 均为 100%，HTTP failure 为 0%。

完整 60 业务组合/120 transport 请求执行耗时约 660 ms，HTTP p50 3.71 ms、
p95 9.11 ms、p99 11.86 ms。

## 后续限制
