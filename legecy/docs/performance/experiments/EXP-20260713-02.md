# EXP-20260713-02：修复 rankings 预热 EOF

- 所属阶段：1
- 状态：接受
- 日期：2026-07-13
- 假设：服务端崩溃、OOM、数据库异常或 HTTP 超时导致预热 EOF
- 回滚方式：恢复 observed API 的原 write timeout

## 诊断

容器持续运行、没有 OOM，PostgreSQL 没有遗留活动查询；API 日志显示请求实际完成
并返回 `200`，耗时 `17.100s`。根因是 observed API 的 `WriteTimeout=15s`，冷查询
完成时客户端连接已经关闭。

## 修改内容

- 仅将容器化 observed API 的 write timeout 调整为 60 秒，生产默认值不变。
- k6 使用 `phase=warmup|load` 区分预热与正式负载，SLA 只检查 load。

## 结果

| 场景 | 结果 |
|---|---:|
| Redis 空缓存预热 | 约 13.5 秒，HTTP 200 |
| 热缓存 p50 | 约 1.5–3.2 毫秒 |
| 热缓存 p95 | 约 3.5–4.7 毫秒 |
| 正式负载错误率 | 0% |
| 响应大小 | 约 17,468 bytes |

## 结论

EOF 已解决，但 13–17 秒的冷聚合不可接受。下一步是固定数据集并分析
`ListOverallRankings` 的 PostgreSQL 执行计划，而不是继续放宽生产超时。
