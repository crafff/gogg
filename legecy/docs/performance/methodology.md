# 性能实验方法

## 实验身份与目录

每项实验使用不可复用的 `EXP-YYYYMMDD-NN`。同一实验的修改前后结果使用相同
实验 ID，通过 `baseline` 和 `candidate` 区分：

```text
tmp/performance/<experiment>/<variant>/<scenario>-<mode>/run-NN/
```

每个运行目录包含 `metadata.env`、`dataset.env` 和 `k6-summary.json`。实验文档
必须引用参与统计的 run ID，不能只引用“最新一次”。

## 可比性要求

修改前后必须保持以下条件一致：

- API 场景、请求参数、VU 和持续时间。
- cache mode、预热方式和请求调度方式。
- `dataset_id` 与关键字段分布。
- 机器、容器资源限制及依赖版本。
- 除待验证变量外的应用配置。

工作区为 dirty 时，每次运行会保存：

- `git-status.txt`：分支、tracked 变更和 untracked 文件名。
- `git-diff.patch`：未暂存的 tracked 文件差异。
- `git-diff-cached.patch`：已暂存的 tracked 文件差异。

实验结论必须说明哪些差异会影响运行结果。untracked 文件只记录名称，不自动保存
内容，避免把本地数据或密钥归档；如果运行依赖 untracked 文件，应先将其纳入 Git，
或使用明确、安全的方式另行归档。无法解释或无法还原运行相关差异时，该结果不能
作为正式基线。只有文档等明确无关的变更时，可以说明后继续使用该结果。

## 重复与统计

1. 执行一次环境预热，不计入正式统计。
2. baseline 至少正式运行三次。
3. 只修改一个主要变量。
4. candidate 使用相同条件至少正式运行三次。
5. 使用正式运行的中位数比较，不选择最好的一次。

warm 测试使用持续负载，报告 p50、p95、p99、RPS 和错误率。cold 测试每次清空
本地 Redis 后只执行一个请求，跨至少三次独立运行比较耗时中位数，不报告单次
运行内部没有意义的 p95。

## 必须记录

- 假设、成功条件、停止条件和回滚方式。
- baseline/candidate commit、dirty 状态和 API 镜像。
- 数据集 ID、表规模、代表性参数和环境资源。
- 延迟、RPS、错误率、响应大小、API CPU/内存。
- PostgreSQL 查询时间/读取、Redis 命中率和连接池情况。
- 正确性测试及契约验证。

## 结论规则

- **接受**：达到预先声明的成功条件，正确性通过，资源代价可接受。
- **拒绝**：收益不足、产生回归或无法证明因果关系。
- **需要更多数据**：波动过大、条件不一致或样本不足。

原始数据不提交 Git；实验文档提交中位数、必要的执行计划摘要和可审阅结论。
容量决策和发布门禁不能只依赖本地测试，必须使用生产规模数据和外部压测机。
