# 产品目标如何约束研发 Agent

状态：v2 提案；入口：[总览](../agent-system-design.md)。本文件定义能力和验证，
不替代后续网站架构设计。

## 1. 将全面超越转为可比较结果

比较固定地区、语言、平台、设备、网络、登录状态、数据时间窗和用户任务。
公开网页只能证明展示了哪些能力，不能推断竞品内部架构、内存、成本或实际效果。

2026-09-04 已打开 OP.GG 主站、AI 与桌面页面。官方 AI 页已展示对线指导、
实时提醒、战斗分析与出装建议，因此增加 AI 教练本身不足以构成差异；其有效性
未在本轮实测。[OP.GG](https://op.gg/)、[官方 AI 页面](https://op.gg/ai)

腾讯 101 指定地址已访问，但文本抓取没有取得交互内容，不能据此列缺失功能或
声称速度落后，后续需浏览器实测。[腾讯 101](https://101.qq.com/#/rankings/rift)

差异化假设是更流畅的核心流程、更明确的版本/样本来源、可复查的个人建议及
长期训练反馈。它们是待验证目标，不是已确认竞品空白。网站与桌面端实时功能
分开比较；公开功能声明、亲自测得体验和内部性能证据分别标注。

## 2. 重构前保全能力

当前记忆提供的盘点入口：LoL 英雄统计、版本目录、详情/取胜因素、召唤师查询
与历史、长任务重连、登录、zh-CN/en-US、URL 状态、本地资产、TFT 统计/观察
预览、玩家历史、Team Planner 代码、采集状态、原始归档。
这不是完整代码审计，需通过路由、接口、测试与实际操作补全。

每项建立 capability ID，映射 `当前入口 → 数据输入 → 可见行为 → 不变量 →
验收场景 → 替换组件 → 迁移/回退`。技术实现可推翻，用户要求保留的行为应有
新候选证据；空数据、预览、部分失败、旧版本和匿名状态都在范围内。

迁移前冻结完整 `capability_baseline_revision`；新版本逐 ID 提供保留或替换的
验收证据，遗漏直接阻断整体验收。删除、延期或改变行为需要明确决定，不能因
重构时漏写任务而隐式发生。修正基线也需记录理由和受影响验收，不重定义成功。

LoL 初始 KR/NA1 与 TFT 平台覆盖分别记录。对标中国区产品并不自动获得同等
区域数据；数据可得性、覆盖和使用条件需单独核实。

## 3. 专家与验收矩阵

| 目标 | 主要专家 | 验收问题 |
|---|---|---|
| 功能保全 | 执行路径 + 验证 | 原用户任务及失败状态是否仍可完成？ |
| 体验优势 | 产品/UX + 浏览器 | 任务成功、理解度、移动端和无障碍如何？ |
| 单机性能/内存 | 性能/可靠性 | 同负载吞吐、延迟、错误率和资源趋势如何？ |
| 抓取/多机恢复 | 可靠性 + 数据 | 取消、重复、限流、重启和接管是否正确？ |
| 历史归档 | 数据 + 验证 | 输入、解析版本和结果能否重现？ |
| 个性化推荐 | 统计/推荐 + 产品 | 是否优于人气、全局胜率、玩家熟练度基线？ |
| 取胜因素 | 统计 + 领域审查 | 描述、预测还是干预结论，证据够不够？ |
| 玩家提升 | 推荐 + 用户研究 | 建议可执行吗，后续行为与技能是否改善？ |

浏览器证据含截图、交互和失败情形。自动检查与代表性用户/专家评估各有职责；
人工评估未做时保留验证缺口，不能让 LLM 冒充真实玩家实验。

## 4. 分析能力逐级建设

第一层是数据事实：发生了什么、在哪个版本、多少覆盖、哪些缺失。
第二层是同条件比较：同英雄、位置、段位、版本、对局时点的参考分布。
第三层是预测/个性化：对未来的预测、适配性和不确定性。
第四层是提升建议：可控行为、训练目标、执行追踪及效果验证。

预测贡献或 SHAP 解释不自动证明改变指标能提高胜率。赛后补刀、伤害、装备
可能包含结果泄漏，或本身是胜负进程导致。必须声明可用观察时点、混杂、样本
选择、位置/英雄差异和补丁变化；数据不足保持未知，语言模型不能补造对局细节。

可交付结果示例：同条件样本里，玩家某个可比较时点的行为偏离参考范围；提出
一个具体练习动作，并追踪未来若干场的变化。缺少干预证据时不承诺固定胜率提升。

## 5. 推荐与教练验证

推荐至少比较全局强势、人气、常用/熟练英雄基线，覆盖冷启动、稀疏历史、换位置
和新补丁。按玩家及时间合理划分，限制未来信息；特征、模型和数据版本可追溯。
评估校准、覆盖、分组质量、解释忠实性与用户偏好。

每种推荐固定决策时点、当时可选集合、可见特征、目标人群和结果窗口。历史只
观察玩家实际选择，不能据此直接证明换选未使用的英雄更好。缺少可识别的策略
评估条件时，离线成绩仅声明预测/排序能力，实际收益需前瞻性比较。数据划分及
不确定性计算考虑同一玩家、同一对局的相关性，不能把十名参赛者视为十份独立证据。

建议以源数据和分析结果为依据，LLM 负责解释与交互，每条建议关联允许使用的
数据窗口、分析版本和观察。建议数量和优先级服从玩家可执行性。

离线通过后再进行授权的专家盲评、用户试验或前瞻性实验。短期胜率受匹配、
队友、对手、段位、版本和自然波动影响，同时衡量行为目标、采纳、理解、技能
指标和长期结果。点击率或文本好评不能单独证明提升有效。

## 6. 性能和历史可复现

记录硬件、限制、软件版本、固定数据、冷热缓存、并发、持续时间、延迟分布、
吞吐、错误率、RSS、heap/分配、CPU、I/O 和存储增长。研发模型用量与网站资源
分开核算，最强研发模型不意味着线上每次页面请求都要调用 LLM。

原始采集、解析器、特征、统计发布、推荐模型和建议模板分别有 revision；数据
manifest 记录来源、时间窗、覆盖、校验和与处理链。研发实验引用这些 ID，不将
业务数据塞进工程记忆或复制成无来源样本。

具体 SLO、单机容量和全面超越的完成标准需基线测量与产品任务确定。本设计
不在没有设备、负载和用户证据时填写看似精确的承诺数值。
